# pointwise-delivery：行展开门户的可信采集演示

一个从零实现的端到端演示：**本地业务门户**（支持行展开，汇总与明细来自不同接口，源数据在查看期间持续变化）→ **浏览器采集器**（真实 Chromium 驱动，把筛选条件 / 展开请求 / 实际返回绑定成证据）→ **核对服务**（检查证据是否属于同一批数据，决定入库）→ **追溯页**（逐行证据链，显式展示限制）。

所有数据均为虚构。

## 核心规则（两条红线）

1. **不用"汇总金额 == 明细合计"代替明细完整。** 金额勾稽只是一个参考信号（页面上单独一列标注"参考"）；行状态只由绑定检查 + 行版本一致性决定。即使金额恰好相等，版本不一致或绑定失败的证据也不采信（见 `test/verify.test.js`）。
2. **展开失败 ≠ 没有明细。** 明细请求超时 / 5xx 记为"明细获取失败"（`incomplete`），绝不记为 0 条明细；证据原件中响应为 `null`，不伪造空明细。

**来源不给统一快照时**：门户的 summary 与 details 各自看到当时的行版本，没有跨接口快照令牌。核对服务的策略是**反复核对**（重新获取证据，最多 3 轮）；仍不一致的行**保留为"不确定"批次**，两个版本的证据都入库，页面顶部以横幅显式展示限制说明。行一旦到达终态（已核对/不确定/明细缺失）即闭环，之后源数据继续变化只追加提示事件，不重开批次。

## 组件

| 目录 | 说明 |
|---|---|
| `portal/` | 业务门户（node:http 零依赖）。虚拟滚动列表（DOM 槽位复用）、行展开明细、`/api/summary` 与 `/api/rows/:id/details` 两个独立接口、每行独立 `rowVersion`、`/api/chaos` 演示控制（注入变更/明细超时/后台变更） |
| `collector/` | 浏览器采集器（playwright-core + Chromium）。驱动真实页面滚动与点击展开；给每个 API 请求注入 `x-collect-action: runId:动作号` 关联头；行身份只认 `data-row-id` 不认 DOM 节点；超时记为获取失败；JSONL 断点续传 |
| `verifier/` | 核对服务 + SQLite 存储（`node:sqlite`）+ 追溯页。绑定检查（筛选条件回显、关联回显、请求↔响应行一致）→ 行版本一致性判定 → 幂等入库（`artifact_id` 主键）→ 逐行证据链 API |
| `demo/` | 编排器：依次演示四个场景并断言 |
| `test/` | 核对逻辑单测（node:test） |

## 证据绑定方式

- **筛选条件**：门户在每个 summary 响应里回显 `filterEcho`，与批次声明的筛选条件比对，不符则整页拒收（不进任何行的证据链）。
- **展开请求 ↔ 实际返回**：采集器经 `page.route` 给每个 API 请求注入 `x-collect-action: <runId>:<动作号>`；门户在响应里回显 `collectAction`。核对服务校验回显属于本次运行，明细响应的 `rowId` 与请求 URL 的行一致。
- **同一批数据**：每行有独立 `rowVersion`；明细版本 == 最新汇总版本才算一致，不一致先反复核对（重取汇总/明细），3 轮后仍不一致则保留不确定。

## 运行

```bash
# 一次性准备浏览器运行环境（无需 root：下载 chromium-headless-shell 与系统库到 .runtime/）
bash scripts/setup-browser.sh

npm test                    # 单测
node demo/run-demo.js       # 完整演示（结束后保留服务，Ctrl+C 结束）
node demo/run-demo.js --no-serve   # 演示完即退出（断言失败时退出码非 0）
```

演示后访问：

- 门户：http://localhost:4100 （虚拟滚动 + 行展开，侧栏可见源数据变化流）
- 追溯页：http://localhost:4200 （批次列表 → 行状态表 → 点击行看证据链时间线；不确定批次顶部有限制横幅）

截图样例在 `demo/shots/`。

## 四个演示场景

| 场景 | 做法 | 验证点 |
|---|---|---|
| A 滚动行复用 | 虚拟滚动 + 后台随机变更 + DO-1007 热点行（每次汇总后立即变更） | 同一 DOM 槽位渲染过多行（证据链可见"DOM 复用"条目）；行身份按 `data-row-id` 归属不串行；DO-1007 三轮核对仍不一致 → 保留为不确定，批次带限制说明 |
| B 某行更新 | `mutate_after_summary`：汇总发出后 DO-1020 立即变更 | 检出版本不一致 → 反复核对 → 版本一致后判已核对，轨迹含 `version_mismatch → version_match` |
| C 明细超时 | DO-1030 首次明细请求挂起 20s | 采集器 6s 判定超时，记"获取失败"（证据响应为 null，不伪造空明细）；重试成功后判已核对；任何时刻不把超时当无明细 |
| D 采集器重启 | 采集到 ~16 行终态后 SIGKILL，同一 run-id 重启 | 断点续采（终态以核对服务为准恢复）；两次启动均留痕；证据入库幂等无重复；未大面积重复展开 |

## 逐行追溯

追溯页点击任意行，时间线展示该行的全部证据与判定：

- 汇总捕获（页 offset、行版本、`requestId`）
- 展开点击（动作号）→ 明细捕获（版本、明细行数、`requestId`）或超时/失败记录
- DOM 槽位复用记录（槽位 #k 在何时渲染了本行）
- 状态迁移（`pending → rechecking → verified/uncertain/incomplete`）及原因
- 采集器启动/重启、终态后源数据继续变化的提示事件

## 已知限制（演示范围）

- 批次终态是粘性的：行闭环后源数据再变只记提示事件；要刷新需开新批次。
- 金额勾稽列仅作参考展示，不参与判定（这是刻意的，见红线 1）。
- 门户的 chaos 接口仅用于演示注入，真实场景对应源系统的自然变更与抖动。
